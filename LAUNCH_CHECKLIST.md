### 5. In-memory rate-limit на логин → Upstash Redis — ВЫПОЛНЕНО (2026-09-11)

Текущая защита от подбора пароля (`src/lib/login-rate-limit.ts`) живёt в памяти одного
процесса — на нескольких serverless-инстансах Vercel (что будет уже при небольшом
реальном трафике) каждый инстанс считает попытки отдельно, и лимит из «5 попыток»
превращается в «5 попыток на инстанс», то есть по факту не работает.

**Сделано:** `src/lib/login-rate-limit.ts` переписан на `@upstash/redis` (не
`@upstash/ratelimit` — наши проверки асимметричны: «заблокирован ли email» и «записать
провал» это раздельные вызовы, а не единый gate-and-consume, под который заточен
`Ratelimit.slidingWindow`). Ключи `login-fail:*` / `login-block:*` с TTL 15 минут —
блокировка автоматически снимается по истечении TTL, ручная зачистка (`sweepStaleEntries`,
`MAX_TRACKED_EMAILS`) больше не нужна, Redis делает это сам. Сигнатуры
`recordFailedLogin`/`clearLoginAttempts`/`getBlockedMs` остались теми же (стали `async`),
вызовы в `src/auth.ts` и `src/app/admin/login/actions.ts` обновлены на `await`.
`npm run build` и `npm run lint` чистые.

⚠️ **Не протестировано на реальном Upstash end-to-end** — тестировал через анонимную
одноразовую Upstash-базу (`upstash.com/start-redis`, без регистрации, живёт 3 дня), но
песочница инструмента блокирует исходящие HTTPS-запросы к её хосту (`ConnectTimeoutError`),
так что живой сетевой вызов Redis не прошёл. Логика проверена: `npm run build`/`npm run lint`
чистые, и то же самое поведение (5 попыток → блок на 15 мин) подтверждено вживую через
Playwright на предыдущей in-memory реализации (см. пентест-чеклист ниже, пункт 1) — сама
Redis-версия использует идентичную арифметику (`INCR`+`EXPIRE`+порог), просто с другим
хранилищем. **После добавления реальных `UPSTASH_REDIS_REST_URL`/`_TOKEN` в Vercel env
(п.0 таблица) обязательно повторить пункт 1 пентеста на живом проде.**

### Content-Security-Policy — ВЫПОЛНЕНО (2026-09-08)

Реализовано в `src/proxy.ts`: nonce на каждый запрос генерируется через
`crypto.randomUUID()`, пробрасывается и в заголовок запроса (`x-nonce` +
`Content-Security-Policy`, чтобы Next.js сам проставил nonce на свои
фреймворк-скрипты/гидратацию), и в заголовок ответа (чтобы браузер применял политику).
Все роуты в проекте и так `ƒ` dynamic — требование «только динамический рендеринг»
для nonce уже выполнено само по себе, ничего дополнительно не потребовалось.

`script-src` — строгий, с nonce + `strict-dynamic` (без `unsafe-inline`) — это и есть
защита от инъекции `<script>`. `style-src` осознанно оставлен на `'unsafe-inline'`, а
не на nonce: Base UI/shadcn (диалоги, дропдауны, select) выставляют инлайн `style=""`
через JS во время выполнения для позиционирования попапов — CSP-нонсы работают только
для `<style>`-тегов, присутствующих при парсинге страницы, а не для рантайм-мутаций
атрибута `style` на элементе, так что nonce для style-src сломал бы эту часть UI.
