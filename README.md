# Jumma Time

Веб-платформа для мечетей: пятничные хутбы, сунны пятницы и другие материалы на трёх языках — **казахском, русском и английском**.

Миссия — помочь прихожанам лучше понимать и сохранять содержание пятничной хутбы (особенно тем, кто не владеет казахским на достаточном уровне), и дать имамам простой инструмент для публикации материалов.

---

## Статус проекта: MVP готов

Это первая рабочая версия (MVP), реализующая весь функционал, описанный в исходном концепте продукта. Тестовый деплой поднят (см. [«Деплой»](#деплой)), но проект **не готов для реальных прихожан** — перед этим требуется:

- наполнение реальным, проверенным имамами контентом (сид-данные — тестовые примеры);
- смена паролей демо-админов и продакшен-`AUTH_SECRET` на текущем деплое (сейчас там всё ещё значения из этой инструкции по настройке);
- шариатская проверка формулировок (это прямо обозначено как риск в исходном концепте).

Функционально всё, что описано в разделе «MVP-функционал» концепта, реализовано и протестировано вручную в браузере — десктоп и мобильная вёрстка (390px), все 30 комбинаций публичных страниц × языков, полный CRUD в админке, вход/выход и граничные случаи сессии.

## Технологический стек

Проект — **full-stack Next.js-монолит** (фронтенд и бэкенд в одном приложении, один деплой), а не связка «отдельный React SPA + отдельный Express API», как было в исходном концепте. Это решение осознанно выбрано вместо изначально предложенного `React + Node/Express + MongoDB`, так как для MVP с одним разработчиком это быстрее в разработке, проще в деплое и не требует поднимать/поддерживать два сервиса и CORS.

| Область | Технология | Зачем |
|---|---|---|
| Фреймворк | **Next.js 16** (App Router, React 19, TypeScript) | Один проект для фронта и бэка, SSR из коробки, файловая маршрутизация |
| Стили / UI-кит | **Tailwind CSS v4** + **shadcn/ui** (на базе [Base UI](https://base-ui.com), не Radix) | Быстрая сборка интерфейса, доступные компоненты, легко кастомизировать под фирменную палитру |
| Локализация | **next-intl** | Маршруты `/kk`, `/ru`, `/en`, серверные и клиентские переводы, переключатель языка |
| База данных | **SQLite** локально (файл `dev.db`), **Turso** (тот же libSQL) в деплое — через **Prisma 7** + **`@prisma/adapter-libsql`** | Prisma 7 требует driver adapter вместо старого движка; libSQL выбран вместо `better-sqlite3`, потому что последний требует нативную компиляцию (node-gyp/Visual Studio), которой нет на машинах без C++ тулчейна. Локально и в проде — один и тот же адаптер, меняются только значения `DATABASE_URL`/`TURSO_AUTH_TOKEN` |
| Авторизация | **NextAuth (Auth.js) v5**, Credentials-провайдер, JWT-сессии (`maxAge` 24 часа), пароли — `bcryptjs`, in-memory rate limit на вход | Простой email/пароль для имама, без внешних OAuth-провайдеров. Сессия короткая осознанно — устройство в мечети общее, не личное |
| Формы/валидация | **Zod** + React Server Actions (`useActionState`) | Валидация на сервере без отдельного REST-слоя |
| QR-код | **`qrcode`** | Генерация QR на лету на сервере (страница `/qr`) |
| Хостинг | **Vercel** (Hobby, бесплатно) + **Turso** (free-тариф) | Тестовый деплой уже поднят — см. раздел «Деплой» |

### Особенности версий (не как в обучающих данных большинства LLM)

Часть используемых библиотек — свежие мажорные версии с ломающими изменениями по сравнению с тем, что типично «знают» языковые модели. При работе с кодом это стоит держать в голове (см. также `AGENTS.md`):

- **Next.js 16**: файл `middleware.ts` переименован в `src/proxy.ts` — это тот же обработчик (next-intl), просто новая file convention. Экспорт остался default-функцией.
- **Base UI** (`@base-ui/react`, на нём собран `shadcn/ui` в этом проекте) — это **не Radix UI**. Две конкретные ловушки, обе уже словленные в этом проекте:
  - У `Menu.Item` нет пропса `onSelect`, только `onClick` (в Radix — наоборот). Если код выглядит «как обычно для shadcn», но клик по пункту меню ничего не делает — велика вероятность именно этой путаницы.
  - `Select.Value` **не подтягивает автоматически** текст выбранного `Select.Item`, как в Radix — без явного `children`-пропса (функции `(value) => label`) он показывает сырое значение (`"SUNNAH"`, `"kk"`) вместо человекочитаемой подписи. Смотри `<SelectValue>{(value) => LABELS[value]}</SelectValue>` в `khutbah-form.tsx` / `content-form.tsx` как референс.
- **Prisma 7**: нужен driver adapter (`@prisma/adapter-libsql` для SQLite/Turso), «голый» `DATABASE_URL` без адаптера не заработает.

**Своя ловушка проекта, не библиотечная:** сессии NextAuth — это JWT (`session: { strategy: "jwt" }`), а не запись в БД. Если добавить новое обязательное поле в `session.user` (как `mosqueId` при добавлении мультимечетности), у пользователей с уже открытым браузером останется старый cookie **без** этого поля — приложение должно быть готово встретить `session` без ожидаемого поля, а не считать, что раз `session` не `null`, то и всё остальное на месте. Иначе (ровно это раз и произошло при разработке) страница логина и защищённый layout начинают бесконечно редиректить друг на друга.

Решено через `src/lib/session-version.ts`: константа `SESSION_VERSION`, которой при входе штампуется JWT, и хелпер `isSessionValid(session)`, проверяющий и версию, и наличие `mosqueId`. При следующем изменении состава `session.user` достаточно поднять `SESSION_VERSION` на единицу — все старые cookie автоматически станут «невалидными» везде разом, без необходимости руками находить и чинить каждую страницу, которая их проверяет. Проверка централизована в `src/proxy.ts` (Next.js 16 proxy работает на Node.js, а не на Edge, поэтому там можно спокойно вызывать `auth()` с обращением к Prisma) — невалидная сессия отправляется на `/admin/login` ещё до рендера любой страницы админки; `layout.tsx` и `login/page.tsx` дублируют ту же проверку тем же хелпером как второй рубеж защиты.

**Rate limit на `/admin/login`** (`src/lib/login-rate-limit.ts`) — 5 неудачных попыток по одному email блокируют его на 15 минут, в памяти процесса (`Map`), без внешних зависимостей. Это защищает от подбора пароля к конкретному, публично известному admin-email (он уже светится в этом README), но **не переживёт деплой на несколько serverless-инстансов** — счётчик привязан к памяти одного процесса. Перед реальным продакшеном на Vercel с несколькими инстансами стоит заменить на что-то общее для всех инстансов, например `@upstash/ratelimit` с Upstash Redis. Счётчик также подчищает сам себя (`sweepStaleEntries`), когда набирает больше 5000 разных email — иначе атакующий мог бы годами копить в памяти по одной записи на каждый случайный/несуществующий email и медленно вытеснять память процесса.

## Безопасность

Репозиторий публичный на GitHub, поэтому исходники не место для секретов — ниже то, что было целенаправленно проверено и почему это безопасно (или было небезопасно и исправлено).

- **`.env` никогда не попадал в git.** `.gitignore` исключает `.env*` (кроме `.env.example`) с первого коммита; проверено по всей истории (`git log --all -- .env`, `git ls-tree` по всем коммитам) — ни разу не закоммичен, утечки нет. В репозитории лежит только `.env.example` с примерами значений, включая пароли демо-админов (`ChangeMe123!`) — они и задуманы как «сразу видно, что надо сменить», но перед реальным деплоем это нужно явно сделать (см. «Статус проекта» выше) — сид не годится для продакшена как есть.
- **IDOR в `/api/khutbahs` — найден и исправлен.** Этот публичный JSON-эндпоинт (используется страницей «Сохранённое» для подгрузки хутб по сохранённым slug'ам) фильтровал только по `publishedAt`, но **не по мечети** — то есть отдавал опубликованные хутбы вообще всех мечетей разом, в обход всей мультимечетной изоляции, описанной выше в разделе «Мультимечетность». Теперь эндпоинт резолвит текущую мечеть из cookie `mosque` тем же способом, что и остальные публичные страницы, и фильтрует по `mosqueId` (`src/app/api/khutbahs/route.ts`). Заодно перепроверены все остальные пути, где ID приходит от клиента (обновление/удаление хутбы и материала в админке, `src/app/admin/(protected)/khutbahs/actions.ts`, `.../content/actions.ts`) — везде уже стоит `mosqueId: session.user.mosqueId` в `where`, точечных дыр не найдено.
- **Секретов на фронтенде нет.** Ключей OpenAI или любых других внешних API в проекте вообще не используется — grep по `OPENAI`, `apiKey`, `NEXT_PUBLIC_*_KEY` по всему `src/` ничего не находит. Если в будущем добавится интеграция с внешним API (например, для помощи в написании хутбы) — ключ должен читаться только на сервере (Server Action / Route Handler), никогда через `NEXT_PUBLIC_`-переменную, иначе он попадёт в JS-бандл браузера и будет виден любому через DevTools, а не только через утечку в репозитории.
- **HTTP security headers** (`next.config.ts`) — `X-Frame-Options: DENY` (защита от clickjacking), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` без камеры/микрофона/геолокации (сайт их не использует). Полноценный `Content-Security-Policy` осознанно не добавлен — Next.js встраивает RSC-данные в inline `<script>` при гидратации, и правильный CSP под это требует nonce-based подхода, который проще настраивать вместе с реальным хостингом (Vercel), а не вслепую.
- **Ссылка на логотип мечети** (`Mosque.logoUrl`, `/admin/settings`) теперь валидируется на `http://`/`https://` в начале строки (`src/app/admin/(protected)/settings/actions.ts`) — раньше `z.url()` пропустил бы синтаксически валидный, но бессмысленный для `<img src>` URL вроде `javascript:...` или `data:...`. Реальный риск был низким (браузеры не исполняют `javascript:` из `img src`, а поле доступно только залогиненному имаму), но проверка на схему — дешёвая защита в глубину.
- **Нет SQL-инъекций.** Весь доступ к БД — через типизированный Prisma Client; `$queryRawUnsafe`/`$executeRawUnsafe` нигде в коде приложения не используются (только в сгенерированных тайпингах самого Prisma).
- **Нет stored XSS.** Ни разу не используется `dangerouslySetInnerHTML` — весь пользовательский текст (заголовки/тексты хутб и материалов) рендерится через обычный JSX и автоматически экранируется React.
- **User-enumeration на логине не протекает.** И «пользователь не найден», и «неверный пароль» в `src/auth.ts:authorize` возвращают одинаковый `null`/одинаковое сообщение об ошибке — по ответу нельзя понять, существует ли email в системе.

**Чек-лист перед реальным использованием текущего деплоя** (помимо уже сказанного в «Статус проекта»): сменить `AUTH_SECRET` и оба демо-пароля прямо в переменных окружения Vercel (сейчас там ещё значения из этой инструкции по настройке — они были нужны только чтобы поднять и проверить деплой), не оставлять `SEED_ADMIN*_PASSWORD` со значениями из `.env.example`, и — если трафик вырастет и Vercel перейдёт на несколько serverless-инстансов — заменить in-memory rate limit на Upstash Redis (см. выше).

## Функционал

### Публичная часть (доступна без входа)

Все страницы локализованы (`/kk/...`, `/ru/...`, `/en/...`), с переключателем языка в шапке.

**Мультимечетность.** Платформа обслуживает сразу несколько мечетей на одном деплое. В шапке рядом с языком — переключатель мечети (виден только если мечетей больше одной); выбор запоминается в cookie `mosque` на год. Хутбы и материалы разделов (сунны, рекомендации, напоминания, достоинства пятницы, вводный блок Аль-Кахф) принадлежат конкретной мечети и видны только когда она выбрана — прямая ссылка на хутбу чужой мечети отдаёт 404. Сами 110 аятов Аль-Кахф — общие для всех мечетей (это текст Корана, а не контент конкретной общины). На узких экранах (мобильный) у переключателей мечети и языка скрывается текстовая подпись, остаётся только иконка — иначе на мобильных ширинах шапка (лого + два переключателя + бургер-меню) не помещается и вызывает горизонтальный скролл.

| Страница | Маршрут | Описание |
|---|---|---|
| Главная | `/{locale}` | Приветствие, плашка мечети (логотип/значок, название, имам, значок «Официальная страница мечети» — см. ниже), кнопки «Смотреть хутбы» / «QR-код мечети», хутба недели (текущей мечети), карточки-разделы |
| Каталог хутб | `/{locale}/khutbahs` | Список опубликованных хутб (все периоды), поиск по названию/дате |
| Хутба | `/{locale}/khutbahs/[slug]` | Полный текст на выбранном языке, кнопки «Сохранить» / «Поделиться» / **«Распечатать»**, регулировка размера текста кнопками **A− / A+** (сохраняется между хутбами) |
| Сохранённые | `/{locale}/saved` | Список хутб, сохранённых на этом устройстве |
| Сунны пятницы | `/{locale}/sunnah` | Список рекомендованных действий из сунны |
| Рекомендуемые действия | `/{locale}/recommended-actions` | Что стоит сделать в пятницу |
| Напоминания | `/{locale}/reminders` | Важные напоминания (например, час принятия дуа) |
| Сура Аль-Кахф | `/{locale}/al-kahf` | Вводный текст о достоинстве чтения суры + **полный текст всех 110 аятов** прямо на странице: арабский оригинал (издание Усмани), транслитерация и перевод. Внизу — дополнительная ссылка на Quran.com |
| Достоинства пятницы | `/{locale}/friday-virtues` | Материалы о статусе пятницы в исламе |
| QR-код мечети | `/{locale}/qr` | QR-код на главную страницу — для печати на стенде мечети |

**Важно про «Сохранённое»:** по концепту не предполагалась полноценная регистрация обычных пользователей, поэтому сохранение хутб реализовано через `localStorage` браузера (без БД, без аккаунта). Это сознательное упрощение MVP — см. раздел «Что дальше». Из-за этого на странице «Сохранённое» (`src/components/site/inapp-browser-warning.tsx`) показывается предупреждение, если сайт открыт во встроенном браузере Instagram/Telegram/WhatsApp/TikTok и т.п. (определяется по `navigator.userAgent`) — у таких webview своё изолированное хранилище, не связанное с обычным Safari/Chrome на устройстве, поэтому сохранённое там может «пропасть» при переходе в настоящий браузер. Предупреждение просто просит открыть ссылку в обычном браузере — технически обойти изоляцию хранилища webview нельзя.

**Печать («имам читает с листа A4 на минбаре»).** Кнопка «Распечатать» на странице хутбы вызывает `window.print()`; вся хромовая часть интерфейса (шапка, меню, кнопки, ссылка «назад») скрыта через утилиту `print:hidden` — Tailwind CSS уже поддерживает `@media print` из коробки без отдельного стиль-листа. Остаётся только дата, заголовок, краткое описание и текст — крупным чёрным текстом на белом фоне (`src/components/site/print-button.tsx`, `src/app/globals.css`).

**Размер шрифта (доступность для старшего поколения).** Кнопки A− / A+ на странице хутбы (`src/components/site/khutbah-body.tsx`) переключают размер текста хутбы между 7 шагами (16–32px), выбор хранится в `localStorage` через `useSyncExternalStore` (тот же паттерн, что и у «Сохранённого») — значит, применяется на всех хутбах сайта, а не только на текущей.

**Брендинг мечети.** На главной странице под приветствием — плашка с логотипом мечети (или значком-заглушкой, если логотип не загружен), названием, именем имама (берётся из `AdminUser.name` привязанного к мечети админа) и значком «Официальная страница мечети». Логотип задаётся ссылкой на изображение в `/admin/settings` — см. ниже. Официальный логотип ДУМК сознательно не встроен: у платформы нет разрешения использовать реальный товарный знак государственной/религиозной организации без предоставленного файла, поэтому вместо этого показывается нейтральный знак доверия.

### Админ-панель (для имама)

Защищённая логином часть на `/admin` (вне языковых префиксов, интерфейс на русском).

**Один админ-аккаунт = одна мечеть.** У каждого `AdminUser` есть `mosqueId`; сессия (JWT) несёт этот `mosqueId`, и все списки/формы/действия в админке молча отфильтрованы по нему — имам мечети «Байкен» не видит хутбы и материалы мечети «Абу-Бакр», даже зная прямую ссылку на них (сервер отвечает 404). В боковой панели название своей мечети показано под логотипом. Ролей внутри одной мечети (главный имам/модератор) нет — см. «Что дальше».

| Страница | Маршрут | Описание |
|---|---|---|
| Вход | `/admin/login` | Email + пароль (NextAuth Credentials). Если в браузере лежит «сломанная» сессия — cookie без `mosqueId` (например, оставшийся с версии до мультимечетности) — страница не редиректит молча, а показывает баннер с кнопкой «Выйти», чтобы всегда был способ выйти из битого состояния и войти заново |
| Обзор | `/admin` | Дашборд: количество хутб и материалов по разделам своей мечети |
| Хутбы — список | `/admin/khutbahs` | Таблица хутб своей мечети (черновики и опубликованные) |
| Хутбы — создание/редактирование | `/admin/khutbahs/new`, `/admin/khutbahs/[id]` | Форма с вкладками по языкам (kk/ru/en): заголовок, краткое описание, полный текст; дата, slug (URL, можно сформировать кнопкой из даты и заголовка), язык оригинала, статус публикации. На каждой вкладке — кнопка **«Предпросмотр»**, открывающая модальное окно с тем, как хутба будет выглядеть на телефоне прихожанина (`khutbah-preview-dialog.tsx`), с точным текущим текстом формы, ещё до сохранения |
| Разделы сайта — список | `/admin/content` | Материалы своей мечети (сунны, рекомендации, напоминания, достоинства пятницы, Аль-Кахф) по вкладкам-категориям |
| Разделы сайта — создание/редактирование | `/admin/content/new`, `/admin/content/[id]` | Та же логика: вкладки по языкам, категория, порядок сортировки, статус публикации |
| Настройки | `/admin/settings` | Ссылка на логотип мечети (показывается на главной странице сайта), название мечети — только для просмотра (меняется в БД) |

Всё через **Server Actions** (без отдельного REST API для CRUD), с серверной валидацией через Zod и понятными сообщениями об ошибках в форме.

**Запланированная публикация.** У хутбы и материала раздела вместо булева `published` — поле `publishedAt: DateTime?` (`src/lib/published.ts`). В форме это выбор из трёх состояний: «Черновик» (`null`, не видно на сайте), «Опубликовано» (текущее время) или «Запланировано» (конкретные дата и время через `datetime-local`). Публичные страницы фильтруют записи условием `publishedAt <= now()` — оно на уровне SQL само отсекает и черновики (`NULL`), и то, что ещё не наступило, одним условием (`publishedWhere()`). Смысл: имам может в среду написать хутбу на пятницу и поставить время публикации на пятницу утром — текст сам появится на сайте в нужный момент, не нужно быть за компьютером или телефоном ровно в момент публикации.

**Заполнение на нескольких языках необязательно.** И для хутбы, и для материала раздела достаточно заполнить заголовок и текст **хотя бы на одном** языке — остальные локали автоматически покажут этот же текст с пометкой «перевод пока не готов» (см. `pickTranslation` выше), пока перевод не добавлен. В форме вкладки языков помечаются галочкой по мере заполнения, а счётчик под подсказкой показывает «заполнено N из 3».

### Модель данных (Prisma, `prisma/schema.prisma`)

```
Mosque               — мечеть (slug, name, logoUrl, order)
AdminUser            — имам/администратор (email, passwordHash), mosqueId — принадлежит одной мечети
Khutbah              — метаданные хутбы (slug, date, publishedAt, originalLocale), mosqueId — принадлежит одной мечети
  └ KhutbahTranslation — перевод хутбы (locale, title, summary, body) — по одной записи на язык
ContentBlock         — материал раздела (category: SUNNAH | RECOMMENDED_ACTION | REMINDER | FRIDAY_VIRTUE | AL_KAHF, order, publishedAt), mosqueId — принадлежит одной мечети
  └ ContentTranslation — перевод материала (locale, title, body)
QuranAyah            — один аят суры (surahNumber, ayahNumber, textArabic, transliteration) — общий для всех мечетей, без mosqueId
  └ QuranAyahTranslation — перевод аята (locale, text) — kk, ru и en
```

Перевод на конкретном языке может отсутствовать — публичные страницы в этом случае автоматически показывают текст на языке оригинала (для хутб — язык оригинала хутбы) с пометкой «перевод пока не готов» там, где применимо (см. `src/lib/i18n-content.ts:pickTranslation`).

Текущая мечеть посетителя определяется в `src/lib/mosque.ts:getCurrentMosque` — по cookie `mosque` (слаг), а если её ещё нет, по первой мечети в порядке `order`. Смена мечети — server action `src/lib/mosque-actions.ts:setMosqueCookie`, вызываемая из клиентского переключателя в шапке.

**Данные Корана** (`prisma/data/al-kahf.json`) — арабский текст (издание `quran-uthmani`), английская транслитерация (`en.transliteration`) и переводы на все три языка платформы: казахский Халифы Алтая (`kk.khalifahaltai`), русский Эльмира Кулиева (`ru.kuliev`) и английский Saheeh International (`en.sahih`) — полученные через публичный [alquran.cloud API](https://alquran.cloud/api) и один раз сохранённые в файл, так что во время `db:seed` сеть не требуется. Как и весь остальной контент, эти переводы стоит сверить с имамом перед боевым использованием.

## Деплой

Тестовый деплой уже проверялся и работал (Vercel + Turso, полный прогон: главная, каталог хутб, вход в админку, чтение из БД — всё отвечало корректно). Сейчас он **сознательно удалён** — рано было держать сайт публично живым с демо-контентом и демо-паролями. База на Turso и код на GitHub при этом никуда не делись — поднять деплой заново можно за несколько минут по шагам ниже.

- **Фронт+бэк**: Vercel (Hobby-план, обычное Next.js-приложение, деплоится без доп. настроек сборки).
- **База данных**: [Turso](https://turso.tech) — тот же libSQL-протокол, что и локальный SQLite, адаптер `@prisma/adapter-libsql` не менялся, поменялись только значения окружения:
  - `DATABASE_URL` — адрес базы вида `libsql://<имя>.turso.io` (без `authToken` в самой строке).
  - `TURSO_AUTH_TOKEN` — отдельная переменная. `src/lib/prisma.ts` и `prisma/seed.ts` передают её вторым полем в `PrismaLibSql({ url, authToken })` — для локальной разработки (`file:./dev.db`) она просто не задана и адаптер её игнорирует.
- **Важная особенность: `prisma migrate deploy` не умеет накатывать миграции на Turso напрямую.** Schema-engine Prisma (часть, отвечающая за миграции) понимает только `file:`-пути для SQLite и падает с `P1013: The provided database string is invalid` на схеме `libsql://` — driver adapter's здесь работает только для самого приложения (Prisma Client), но не для CLI-миграций. Рабочий способ: применить готовые `.sql`-файлы из `prisma/migrations/*/migration.sql` напрямую через `@libsql/client` (`createClient({ url, authToken }).executeMultiple(sql)`), по одному файлу на каждую папку миграции по порядку. Так же накатывались и тестовые данные — `npm run db:seed` с `DATABASE_URL`/`TURSO_AUTH_TOKEN`, указывающими на Turso, отрабатывает нормально (сид идёт через обычный Prisma Client, а не через schema-engine).
- **Переменные окружения на Vercel** (Project → Settings → Environment Variables): `DATABASE_URL`, `TURSO_AUTH_TOKEN`, `AUTH_SECRET` — все три со значениями, отдельными от локального `.env` (боевой `AUTH_SECRET` не должен совпадать с dev-версией).
- **GitHub-автодеплой при первой попытке не подключился сам** — импорт репозитория в Vercel через CLI/токен не смог привязать GitHub без ручного разрешения владельца аккаунта на экране авторизации GitHub. Подключить: Vercel → проект → Settings → Git → Connect Git Repository — тогда каждый `git push` будет сам обновлять сайт, без ручных `vercel --prod`.
- **Деньги.** Оба сервиса на бесплатных тарифах и с текущей нагрузкой (несколько тестовых мечетей, единичные посетители) останутся бесплатными: Vercel Hobby — щедрые лимиты на трафик/выполнение функций для некоммерческого использования; Turso free-тариф — с запасом покрывает объём этого проекта (несколько сотен строк). Платить нужно будет только если: (а) трафик реально вырастет far за пределы MVP, либо (б) понадобится Vercel Pro для коммерческого использования под организацией/командой. Банковская карта нигде не привязана — оба аккаунта регистрировались без неё.

Общая логика деплоя на любой другой хостинг (если не Vercel) — та же: поднять БД, прописать переменные окружения, накатить схему, засеять один раз.

## Что дальше (для дальнейшей разработки)

Пункты не реализованы в MVP осознанно (чтобы не раздувать первую версию) — ближайшие кандидаты на доработку:

- **Учётные записи обычных пользователей.** Сейчас «Сохранённое» живёт в `localStorage` устройства — без синхронизации между устройствами. Полноценные аккаунты прихожан — следующий логичный шаг, если появится такая потребность.
- **Загрузка медиа.** Концепт упоминает возможные аудио/видео-версии хутб — сейчас поддерживается только текст.
- **Логотип мечети — по ссылке, не по загрузке файла.** `Mosque.logoUrl` — это просто ссылка на уже где-то размещённое изображение, а не загрузка файла на сервер. Осознанное решение для MVP: на Vercel (serverless) нет постоянной файловой системы для `/public`, так что «загрузка файла» потребовала бы отдельного сервиса (Uploadthing, Cloudinary и т.п.) и API-ключей — решили отложить, пока не будет реальных имамов-пользователей, которым сложно самим разместить картинку по ссылке (например, через Imgur или Telegraph). Ближайший кандидат на доработку, когда встанет вопрос удобства для конечных пользователей.
- **Уведомления/пуши.** Раздел «Напоминания» сейчас статический контент, без реальных push-уведомлений о новых материалах.
- **Роли в админке.** Один `AdminUser` = одна мечеть, но внутри мечети роли не разделены (нет «главный имам» / «модератор» с разными правами).
- **Управление мечетями из UI.** Список мечетей сейчас редактируется только напрямую в БД (`prisma studio` или сид) — нет админ-экрана «создать мечеть + пригласить имама».
- **Английская/русская локализация редакторских уведомлений (toast) в админке** — сейчас интерфейс админки не локализован (это осознанно — рассчитан на одного оператора-имама).
- **Автотесты.** Пока только ручная QA-проверка в браузере, `tsc --noEmit` и `eslint`; unit/e2e-тестов нет.
- **Шариатская вычитка контента.** Все сид-данные (хутбы, материалы разделов) — иллюстративные примеры и должны быть заменены/проверены имамами перед реальным использованием (см. раздел «Вопросы шариатского характера» в исходном концепте). Текст Корана на странице Аль-Кахф взят из признанных изданий (Халифа Алтай, Кулиев, Saheeh International) — тем не менее стоит сверить их с имамом перед боевым использованием.
- **Другие суры.** Модель `QuranAyah` уже поддерживает произвольный `surahNumber`, но сид и UI сейчас рассчитаны только на суру Аль-Кахф (18) — расширение на другие суры потребует доработки страниц.
